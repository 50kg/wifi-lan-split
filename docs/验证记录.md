# 验证记录与未覆盖项目

**简体中文** | [English](en/verification.md)

以下是在作者自己的电脑上做过的验证，环境是 Windows 10，手机热点 Wi-Fi 加公司网线。原始抓包和日志含有内网信息，不随源码公开。

## 断网与续租实测（2026-10-19）

- **内存模式断 Wi-Fi 抓包**：
  - 有线发送：Wi-Fi 在线时 4 包 / 239 字节，断开时 106 包 / 10708 字节；
  - 有线接收：分别为 28 包 / 3819 字节、219 包 / 166026 字节；
  - 计数器、原始 XML 和独立解析的 pcap 帧数及字节数都对得上。
- **断开 Wi-Fi 时的有线发送分类**：ARP 4、UDP 广播 3、到内网网关的 ICMP 1、到内网服务器的 TCP 98；没有观测到公网 IPv4、IPv6 或热点子网的包。公网的 HTTP/HTTPS/TCP/UDP/ICMP/IPv6 探测都失败；绑定有线网卡的 TCP 连接，在 WFP 记录里为拒绝。
- 断网测试前先设置了独立的 Wi-Fi 自动恢复；恢复后 HTTPS 返回 200，临时任务已清理。
- 加入路由看守后，做了三次真实的有线 DHCP 续租（其中一次通过工具后端）。每次检查时有线默认路由都是 0，看守日志记录了自动删除；Wi-Fi 保持连接，HTTPS 正常。
- **重启后一次性检查**：
  - 预检通过（SYSTEM 身份运行）：HTTPS 源地址为 Wi-Fi，远端 1.1.1.1；
  - 真实重启后，审计任务在开机约 1 分钟时生成正式报告，结果为 PASS；
  - 这是配置和代表性连接检查，不是开机全过程抓包。

磁盘/循环模式下出现过计数器和落盘帧数不一致，确有包没有写进原始记录，所以不能把那次的空记录当作“没有流量”的证据。同样的控制实验改用内存模式后，计数和帧数对得上，之后的正式断网测试都用内存模式。没有为了解决抓包问题去修改分流规则。

## Get-Acl 模块加载失败（2026-10-22）

- 用户反馈：每次检查都失败，提示 “The 'Get-Acl' command was found in the module 'Microsoft.PowerShell.Security', but the module could not be loaded”。
- 可能原因一（在作者电脑上复现）：后台继承的模块路径里，PowerShell 7 风格的 `Microsoft.PowerShell.Security` 排在 Windows PowerShell 自带的前面。它的类型文件和 Windows PowerShell 已有的定义重复，加载时报 “The member Path is already present”。`Join-Path`、`Test-Path` 不受影响，所以出错的是脚本里第一个 `Get-Acl`。后台现在只从自带目录加载模块，这一情形已修复。
- 可能原因二（在作者电脑上复现）：后台设了 `$ErrorActionPreference='Stop'`。导入模块时只要冒出一个原本不致命的错误，就会变成同一句报错；这种情况下真正的原因不附在报错上，只记在 `$Error` 里。
- 报告者第一份诊断（第 1 版脚本）：
  - 没装 PowerShell 7，系统级模块路径正常，没有冒名的模块；
  - 两种模块路径下 `Get-Acl` 都正常。
  
  因此不支持原因一。但第 1 版的子进程没有设“出错即停”，在原因二的情形下也会显示“正常”（在作者电脑上用仿造的模块确认过），所以也排除不了原因二。
- 随后的改动：
  - 后台报错时写出原因：带内层异常；没有内层异常时再导入一次模块取得原因；再次导入成功的注明“可能是暂时性问题”。
  - 诊断脚本第 2 版按后台的方式运行，并记录完整的异常链。
  - `tests/Test-ModulePath.ps1` 覆盖了以上情形；它对修复前的 `backend.ps1` 运行会失败，报的正是这个错误。
  - 第 2 版诊断在作者电脑上用三种模块路径运行过（仿 PowerShell 7、正常、导入时出现不致命错误），结论和失败原因都符合预期。
- 之后报告者反馈已经可以正常使用，这些改动随 v1.0.1 发布。
- 未确认：报告者电脑上的真正原因。没有收到能说明原因的日志；如果再出现，新版日志会在报错后面写出原因。

# 架构与安全边界

**简体中文** | [English](en/architecture.md)

## 调用链

`双网分流.exe` → 校验后台文件并放进受保护目录 → 子进程 Windows PowerShell（`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`）→ `C:\ProgramData\WifiLanSplit\app\backend.ps1` → `network-core.ps1`。

界面以管理员身份运行，所以不直接执行程序目录里的脚本：

- 构建时，`backend.ps1`、`network-core.ps1`、`RouteGuard.exe` 的 SHA-256 写进界面程序。
- 每次操作前（包括检查状态），界面读取这三个文件并核对哈希，然后从只有 SYSTEM/Administrators 能写的 `ProgramData\WifiLanSplit\app` 执行。
  - 那里已经有相同且可信的副本时，不重写；
  - 否则把核对过的同一份字节写成临时文件，再整体替换；
  - 程序目录里的文件被改过或缺失时，界面拒绝运行并说明原因。
- 后台的输出不重定向给界面，由后台自己写进数据目录的 `last-operation.log`。关掉窗口不会打断正在进行的修改。
- PowerShell、资源管理器、记事本和控制面板都用系统目录的完整路径启动，不受程序目录或当前目录里同名文件的影响。

数据目录 `C:\ProgramData\WifiLanSplit` 由界面或后台创建。创建时就只授权 SYSTEM 和 Administrators，所有者为 Administrators，不继承 ProgramData 的“用户可以创建文件”权限。

- 目录已经存在、所有者可信但权限过宽时，收紧为上述权限，再逐一检查里面已有的文件；有不可信的所有者或写入权限就停止。
- 所有者不是 SYSTEM、Administrators 或 TrustedInstaller 时，拒绝继续，提示管理员检查。
- 后台在启用、修复、续租、还原之前，同样核对 `state.json` 的所有者和写入权限。所有者是当前管理员本人时（有些电脑把新文件默认归创建者所有），改回 Administrators 后继续；其他情况一律拒绝。
- 本工具写出的 `state.json`、备份副本、看守程序和后台副本，所有者都显式设为 Administrators。

后台 `RouteGuard.exe` 通过 IP Helper 原生接口接收路由通知，不依赖界面是否打开。

## 设置顺序

1. 识别物理网卡，验证 DHCP、地址、网关、DNS 和子网不重叠；有额外的活动适配器（VPN、Tailscale、Hyper-V/WSL/Docker 虚拟网卡）或已有冲突路由时，拒绝继续。
2. 先备份，再修改网络。备份内容：
   - 写入 `state.json`：本机状态、原 DNS、接口开销、被移除的路由、防火墙开启状态；
   - 完整的防火墙导出；
   - `state.json` 的原始副本 `state-at-setup.json`，和防火墙导出一起放在 `backup-*` 目录。
   `state.json` 每次保存都是先写临时文件再整体替换，上一版保留为 `state.json.previous`。替换失败时，保证 `state.json` 仍然存在。
3. 建立防火墙规则，并检查规则已经生效：
   - 作用于所有 Wired 接口、所有配置文件、所有协议和端口；
   - IPv4 阻断 192.168 以外的地址，IPv6 全部阻断；
   - 热点落在 192.168 内时，额外阻断该子网；
   - 有线的有限广播（255.255.255.255）保留给 DHCP；
   - 启用防火墙。
4. 修改路由和 DNS：
   - Wi-Fi 的 IPv4 开销设为 10，有线设为 500，有线另外打开 IgnoreDefaultRoutes；
   - 建立经公司网关的 192.168/16 路由，移除备份里记录的、经网关通往非内网的路由；
   - 有线 DNS 改用当前 Wi-Fi 的 DNS。
5. 在受保护的 ProgramData 目录部署看守，以 SYSTEM 身份创建开机任务。网卡通过 GUID 定位，实际接口编号每一轮都重新读取。

兼容早期版本：

- 早期版本的规则组 `CodexStrictSplit20261016` 只有 3 条出站规则，并且只作用于某一个网卡别名。当前版本使用 `WifiPublicWiredLAN-v2`，出站和入站规则作用于所有 Wired 接口。两者范围不同，审查时要分开看。
- 状态检查会识别早期规则组，并在“防火墙阻断”一项注明“仅限”哪块网卡。这时另一块网线网卡连上，结论会变成“‘网卡名’可以直接上公网”或“没有防火墙保护”。还原时两个规则组都会删除。

## 看守

GetIpForwardTable2 读取 IPv4 路由，NotifyRouteChange2 唤醒检查，DeleteIpForwardEntry2 删除指定有线网卡上前缀长度为 0 的路由；另外每 500 毫秒兜底扫描一次。

- **单实例**：用受保护数据目录里的 `guard.lock` 文件锁实现。不用全局互斥量，因为普通用户可以抢先创建同名互斥量，让看守一启动就退出。只有共享冲突才算“已有看守在运行”，并且会重试 5 秒；其他错误以非零代码退出。
- **出错不退出**：每一轮检查单独捕获异常。读路由表失败、网卡暂时没有 IPv4 等情况只记日志，下一轮重试。路由通知注册失败时，只靠 500 毫秒扫描继续工作。
- **心跳**：只在一轮检查成功后才写。一直出错的看守在状态里显示为“没有运行”，可以点“修复路由看守”重启它。
- **日志**：同类错误每分钟最多写一条，并注明这期间省略了几条；默认路由删除记录每 10 秒最多一条。日志超过 1 MB 时改名为 `route-guard.old.log`。

更新或修复看守的顺序：

1. 旧看守继续运行，先复制新程序并核对哈希；
2. 停止旧进程，开机任务保持注册；
3. 换上新程序。替换中途失败时，放回旧程序并重新启动；
4. 启动任务。只有这一步之后写出的心跳才算启动成功，停掉的旧看守留下的心跳不算；
5. 任务显示在运行、心跳却已过期时，先结束同一路径的旧进程，因为它可能还占着 `guard.lock`。

只有任务指向别的程序，或者监视的不是这块网卡时，才会重新注册任务。

IgnoreDefaultRoutes 在作者的电脑上不能单独阻止续租重新产生默认路由；曾经试过的 DontAddDefaultGateway 无效，已经删除。看守不是同步过滤驱动，无法保证路由表里从不瞬间出现有线默认路由。开机启动延迟和事件处理延迟这段时间，仍靠持久防火墙保护。

## 检查和还原

后台的 Status 只读：读取系统网络配置，写结果文件，不修改任何设置，也不抓包。界面在每次检查前做的准备见“调用链”：确保数据目录受保护、更新 `app` 副本、删除 10 分钟前的结果文件。这些都不涉及网络设置。

启用、修复、续租、还原同一时间只能进行一项：后台在数据目录持有 `operation.lock`，直到进程结束。这期间检查状态会显示“另一项操作正在进行”，界面也不提供任何操作按钮。

检查结果分成一句结论（等级、标题、原因、建议操作）和逐项检查：

- 防火墙阻断：检查实际出站规则的地址、协议、端口、程序、应用包、服务、用户和接口范围，以及所有防火墙配置文件是否开启；
- 网线默认路由条数；
- 路由看守：任务和心跳；
- 正在运行的看守与当前版本是否一致；
- 其他网线网卡是否在阻断范围内、有没有默认路由；
- 不在控制范围内的接口，例如 Tailscale；
- 数据目录权限；
- 备份状态是否完整。找不到 `state.json`、但规则或看守任务还在时，判为错误，不提供“启用分流”，以免把已经改过的设置当成原始设置备份。

只有当问题全部出在看守上时，界面才提供“修复路由看守”。防火墙规则缺失、热点子网变化、另一块网卡未受保护等情况，界面只说明原因和下一步（通常是先还原再重新启用），不假装能自动修复。另一块网卡的情况会提供“打开网络连接”。

Repair 只在防火墙覆盖正常时修复看守，不是全量修复配置。Renew 只续租选定的有线网卡，不做 release，不碰 Wi-Fi。

Restore 的顺序：

1. 核对 Windows MachineGuid 和两张网卡的 GUID；
2. 停止属于本工具的看守；
3. 恢复备份里的参数；
4. 删除本工具和被接管的旧规则组。

GUI 还原不导入完整的旧防火墙，以免覆盖之后无关的修改；完整导出只供应急使用。界面和 `Restore.cmd` 在还原前都要求确认。

## 不能过度宣称

按目标 IP 和网卡控制，可以覆盖正常 Windows 网络栈上的 HTTP、Socket 等通信，与 URL 或端口无关，但不识别应用实际的业务终点。允许访问的内网代理可以替你转发公网。本工具不处理代理，也不管理 Tailscale 等 VPN 或隧道，所以不能宣称整机所有可能的路径都已完全隔离。

作者的电脑上曾验证：断开 Wi-Fi 时没有观测到有线公网包。但这不是对所有时刻的数学证明。下面这些还没有覆盖：

- 跨设备首次安装；
- 真实还原；
- 开机全过程抓包。

固定的热点 DNS、已保存的热点子网和公司网关一旦随环境变化，就需要重新审查。不要把一台电脑的状态直接搬到另一台电脑。

已知的取舍：

- 有线 DNS 换成热点 DNS 后，公司内网域名可能解析不了，内网服务请用 IP 访问。
- 有线只改了 IPv4 的开销和 DNS；有线 IPv6 被防火墙全部阻断，公司网络如果下发 IPv6，相关解析可能变慢。
- 新版规则作用于所有 Wired 接口，可能同时作用于 Hyper-V/WSL/Docker 的虚拟网卡（未验证）。

部署之前也有一段窗口期：首次启用前还没有本工具的防火墙，插上公司网线本身就可能产生公网出口。新电脑应避免在敏感业务运行时首次插线和安装。
